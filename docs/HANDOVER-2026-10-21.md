## 2. The site: how it is put together now

- **Pages** are plain HTML in the repo root (58 today). Each has its own stylesheet with a class prefix. The recipe
  for a new service page is `BUILDING-SERVICE-PAGES.md`; a new page file needs only head + content + `<script
  src="script.js">`; everything shared is stamped in by the build.
- **`node scripts/build.mjs`** (no deps) stamps the shared chrome into every page in place: skip link + header
  (with `aria-current`), breadcrumb, `<main>`, prev/next pager within a page family, the quote-form section, footer,
  chat widget, consent banner, and head metadata (chrome.css link, canonical, Open Graph, LocalBusiness/Breadcrumb
  JSON-LD, cache-busted asset hashes). It also writes `sitemap.xml`, `sitemap.html`, `robots.txt`. Idempotent via
  `<!-- build:x -->` markers; `--check` for CI; `node scripts/build.mjs page.html` for one page (use that while
  other agents/sessions are editing pages — the bare build rewrites every file).
- **Inputs:** `partials/*.html` (header, footer, contact, contact-info, chat, consent), `site/business.json`
  (facts: phone, email, address, hours, service area, Turnstile site key), `site/pages.json` (registry: label,
  parent, order, service preselect, contact lead). New pages are auto-registered on first build; set their parent/
  order/lead there afterwards.
- **`chrome.css`** holds everything the chrome needs (text-size scaling, breadcrumb, pager, consent, chat and form
  states, legal/sitemap/404 layout, `ol[class]{list-style:none}`). `styles.css` is the design system and was only
  touched by `scripts/px-to-rem.mjs` (all `font-size` px → rem, done once; keep new CSS in rem).
- **`script.js`** (rewritten): nav, sliders, carousel, text-size −/+ (5 steps 87.5–137.5 %, `localStorage
  cl-text-scale`, header capped at 112.5 % on desktop and 100 % ≤1100 px), consent banner (`cl-consent`; map
  embed and first-party analytics only after consent), quote form (client validation, photo validation 5 × 10 MB
  JPEG/PNG/WebP, lazy Turnstile, idempotency key, honeypot, real `fetch` to `/api/inquiries`, success only on 2xx
  JSON), chat (greeting + three actions, `/api/chat`, context-aware chips/links, photo upload, hand-off to the form
  with a `sessionStorage` draft, honest offline fallback that answers hours from `site/business.json`).
- **`vercel.json`**: `cleanUrls`, security headers, cache headers, and the legacy 301 map from `PAGE-INVENTORY.md`
  (old Strikingly URLs → new pages). Only takes effect on Vercel.
- **Verified today:** full build idempotent (58 pages, `--check` = 0); no horizontal overflow on any page at 390 /
  768 / 1024 px (sampled pages also at 137.5 % text size); chat and form fail honestly on a static host.

Local preview: `python -m http.server 8788` (static only; POSTs return 501 and the UI shows its offline messages),
or `npm run dev` → http://localhost:8787 with the real API on an embedded PGlite database (zero credentials).

## 3. The backend (site repo `api/`, `lib/`, `db/`, `test/`)

Full reference: `docs/BACKEND.md` and `.env.example`. Summary:

- Endpoints: `POST /api/chat`, `POST /api/uploads`, `POST /api/inquiries`, `POST /api/events`, `GET /api/health`,
  `GET /api/photo` (HMAC-signed, expiring), `GET|PATCH /api/admin/inquiries[/:id]` and `/api/admin/retry-email`
  (Bearer `ADMIN_API_TOKEN`, stopgap until the estimater has real auth).
- Chat is a **server-side state machine** (`lib/chat/machine.ts`): boat → damage → location → kind → where →
  photos → name → email → phone → review card → submit → reference number. Claude only phrases; without a key it
  runs fully scripted. Routing answers first, then offers the matching service page (never the current one).
  Prompt-injection attempts are refused without changing state. Monthly AI budget cap in `ai_usage`.
- Inquiries: rate limit → honeypot → zod → Turnstile `siteverify` → idempotency/duplicate check → DB row (`ref`
  `CL-YYYY-NNNN`) + photos (`bytea`, re-encoded ≤1600 px, metadata stripped) → branded email via Resend (delivery
  row `pending_config` when no key; `retry-email` resends) → audit row. `ok` only after the row exists.
- `npm test` = 26 tests on PGlite (migrations, inquiry paths, Turnstile matrix, upload abuse, chat flow, routing,
  injection, rate limits, events, health, admin). `npm run typecheck` clean. `npm run build:knowledge` regenerates
  `site/knowledge.json` (chatbot knowledge from page copy) — run it after changing page text and commit the result.

Production safety: with `VERCEL_ENV=production` and no `TURNSTILE_SECRET_KEY` the form returns 503 "call us"
(override `ALLOW_UNVERIFIED_FORMS=true` only knowingly). `SESSION_SECRET` must be set before launch.

## 7. Committing in the site repo (parallel sessions)

```bash
cd /c/Users/1234/captain-levis
export GIT_AUTHOR_NAME=Tdizzles GIT_AUTHOR_EMAIL=kjhwtqnf5r@privaterelay.appleid.com GIT_COMMITTER_NAME=Tdizzles GIT_COMMITTER_EMAIL=kjhwtqnf5r@privaterelay.appleid.com
OLD=$(git rev-parse HEAD); export GIT_INDEX_FILE=.git/index-x; git read-tree $OLD; git add -A .   # or only your paths
TREE=$(git write-tree); NEW=$(git commit-tree $TREE -p $OLD -m "message"); unset GIT_INDEX_FILE
git update-ref refs/heads/main $NEW $OLD && git reset -q $NEW && git push origin $NEW:refs/heads/main
```
The `update-ref` is a compare-and-swap: if a peer committed in between it fails and you re-run from the new HEAD.
